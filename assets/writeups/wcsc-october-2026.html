1. [Forensics/IR] The Empire Strikes Back (750) / The Empire's Last Orders

One-line summary: The user analyst downloaded Package-Capa.7z over cleartext HTTP. Inside it was an encrypted archive whose password was the raw base64 string from flag.txt. That archive contained a PowerShell Empire C# agent (capa.exe), which was executed. From the memory dump we recovered (1) the FG= value in the environment block of the decoy process SessionWorker.exe — the Last Orders flag — and (2) a reflectively loaded .NET assembly whose name was a base64 string stored in UTF-16 — the Strikes Back flag.

Attack chain

  1. Initial delivery: analyst downloaded Package-Capa.7z from an external host over cleartext HTTP. The directory listing on that server (10.226.206[.]191:8000) contained only this file. A reverse lookup to eduroam-226-206-191.laptops.usf.edu is recorded in the notes, but the raw lookup output is not in the evidence set.
  2. Social engineering: flag.txt inside the archive reads "The archive is sealed. Maybe the flag you found nearby is the key it's waiting for." together with a base64 string. That raw base64 string is the password for Secret-Package.7z. The decoded WCSC{...} value is not the password.
  3. Execution: Secret-Package/capa.exe (named to impersonate the legitimate capa tool) was executed. Identified as a PowerShell Empire C# agent (Sharpire family).
  4. Decoy process: capa.exe spawned %LOCALAPPDATA%\Temp\ApplicationTelemetry\<GUID-like folder>\SessionWorker.exe 1800. This is a tiny .NET program that only reads an environment variable and sleeps.
  5. Persistence: not established. The scheduled tasks we initially suspected turned out to be lab automation (see "Ruled out" below).
  6. C2: 192.168.175[.]128 over HTTP. We could not recover any actual traffic to this C2.
  7. In-memory module: the dump contains the name of a reflectively loaded .NET assembly that does not exist on disk (the Strikes Back flag). We assess it was loaded via Empire's RunAssemblyInProcess — this is an inference, not a confirmed fact.
  8. Privilege escalation / lateral movement / exfiltration: not established.

Part 1 — The Empire's Last Orders

1. Problem summary

  • Provided: Extraction.7z (KAPE triage + memory dump)
  • Goal: a hidden flag (WCSC{...})

2. Analysis

  • In the triage set, ConsoleHost_history.txt and scheduled-task XML pointed at C:\ProgramData\LabWorker\Windows-Executor.ps1 and the tasks LocalWorker / LocalWorkerWatchdog. These turned out to be lab automation (see "Ruled out").
  • Scanning the whole memory dump in both ASCII and UTF-16LE produced WCSC{echoes_in_freed_memory_64795e1b}. The surrounding context is a process environment block (PEB environment): FG=WCSC{...} followed by PATH, SystemRoot, TEMP, TMP, WINDIR.
  • The same context revealed the SessionWorker.exe path, and execution was cross-confirmed via the prefetch file SESSIONWORKER.EXE-45532A12.pf.
  • Occurrences in the dump: 5 in ASCII, 4 in UTF-16LE. Offsets are in evidence/wcsc-empire/flag_offsets.txt.
  • As the flag name suggests, the environment block of a terminated process was still resident in freed memory.

  1. Review the triage artifacts (ConsoleHost_history, scheduled-task XML, event logs).
  2. Full string search over the memory dump. Define the variables yourself:

  • Time obtained: 2026-10-30 14:20 UTC (23:20 KST) — first entry in notes/FLAGS.md; submission and scoring were done manually by the operator. The recorded time is converted from the workstation's local timezone (Asia/Bangkok, UTC+07).

Part 2 — The Empire Strikes Back (750)

1. Problem summary

  • Provided: the same Extraction.7z as Part 1
  • Goal: a flag (WCSC{...}) derived from a malicious artifact in the dump

2. Analysis

  • Observation: dumping SessionWorker.exe (vol windows.pslist --pid 6720 --dump) yielded a 24 KB PE32+ .NET binary referencing only mscorlib / Environment / Thread. It only calls GetEnvironmentVariable and Thread.Sleep, so it is a decoy rather than malware, and the FG= value it carries (the Part 1 flag) is not the answer here.
  • Actual chain: vol windows.cmdline confirmed PID 8188 capa.exe, PID 6720 SessionWorker.exe, and PID 11416 Notepad.exe (with flag.txt open).
  • Recovered flag.txt from memory: V0NTQ3tmb2xsb3dfdGhlX3N1cHBvcnRfaGFuZG9mZl82YTU1NjI2Nn0= plus the "The archive is sealed..." text. Decoding gives WCSC{follow_the_support_handoff_6a556266} — an incorrect-answer breadcrumb.
  • Extracted Package-Capa.7z from Downloads/Dump.pcapng (tshark --export-objects http). Contents: flag.txt + Secret-Package.7z, with the raw base64 as the password. The capa.exe inside is an Empire C# agent (feature strings: AesEncryptThenHmac, BuildRoutingPacket, ChaCha20Poly1305, CheckAgentJobs, RunAssemblyInProcess, RunPowerShell, etc.).
  • Key insight: the first pass searched for base64 only in ASCII. .NET stores strings as UTF-16, so a V0NTQ3... sequence has a NUL byte between every character and never matches an ASCII pattern. Re-running the search with strings -el produced a new string with 4 occurrences.
  • Location: dump offsets 2120233860, 2120234192, 3954008676, 3954009008 (evidence/wcsc-empire/flag3_offsets.txt). The surrounding data is a CLR assembly load list: 0v2wkbf1.mi4, Version=0.0.0.0, Culture=neutral, PublicKeyToken=null, V0NTQ3thX3dp..., Version=0.0.0.0, ... (the assembly name is the base64 flag), System.Windows.Forms, System.Drawing, mscorlib. This is a reflectively loaded assembly that exists only in memory, never on disk. The references to Windows.Forms/Drawing suggest screen-capture functionality (inference).

3. Steps

Tools used (tools/wcsc-empire/):

  • evtx_scriptblocks.py — reconstructs PowerShell 4104 script blocks from evtx (python3 -I tools/wcsc-empire/evtx_scriptblocks.py <evtx> 4104).
  • fast_scan.py — single pass over the dump looking for WCSC{ under single-byte XOR/ADD, reversal, rot13, UTF-16BE and hex variants. This scan did not find it.
  • scan_encodings.py — python3 -I tools/wcsc-empire/scan_encodings.py <dump>; first version that ran 255 single-byte XOR passes with mmap.find (abandoned as too slow, replaced by fast_scan.py). Also did not find it.
  • The search that actually succeeded was not a script but a one-liner: strings -el $DUMP | grep -oE 'V0NTQ3[A-Za-z0-9+/=]{6,}' (output: evidence/wcsc-empire/enc_scan2.txt).
  • ctx_dump.py — dumps ASCII/UTF-16 strings around a given offset.

Approaches ruled out (none produced a new WCSC hit): plaintext / UTF-16 / reversed / rot13 / hex / base64 (all three alignments) / single-byte XOR and ADD across the whole dump; ASCII + UTF-16 grep over all 769 triage files; plaintext, XOR, ADD, base64, repeating-key XOR with the staging key, and ChaCha20 decryption against capa.exe. capa.exe has no overlay, no extra sections and no resources.

2. [OSINT] Here and There — 500

1. Problem summary

  • Provided: a chat log and two images. No server.
  • Sent by Jake: Screenshot_2026-10-30_033847.png (80 x 87 px)
  • Sent by Jonathan: VERT_IMG_0238.png (2012 x 552 px)
  • Conversation: Jonathan "wya" → Jake sends an image → Jonathan "wtf" → "just come meet me here" + image
  • Task: locate both people, compute the great-circle (straight-line) distance between the two points in miles, rounded to the nearest 10.
  • Driving/route distance is not used. Format: WCSC{distance}
  • Hints (100 points each): "Where Jonathan", "Where Jake?"

Both images are barcodes, but of different kinds. PDF417 carries the data itself; a NaviLens tag carries only an ID that must be resolved against a server, so the registered information has to be looked up separately.

2. Analysis

2-1. Jonathan — PDF417 boarding pass (IATA BCBP)

VERT_IMG_0238.png is a photograph of a printed PDF417 symbol. Decoded with zxing-cpp:

M1KARTWIDJAJA/JONATHANELT0N37 ORDFARUA 5679 298YOVSL0000 177>8320OO6298BUA ...

Split into the fixed-width fields of IATA Resolution 792:

Field Value Meaning
Format Code / Legs M / 1 BCBP, 1 leg
Passenger Name (20) KARTWIDJAJA/JONATHAN
Electronic Ticket Ind E
Operating carrier PNR (7) LT0N37
From City Airport (3) ORD Chicago O'Hare
To City Airport (3) FAR Fargo, Hector International
Operating carrier (3) UA United Airlines
Flight Number (5) 5679 UA 5679
Date of Flight (3) 298 day 298 of the year (no year in the field)
Compartment / Seat Y / OVSL

We read "here" in "just come meet me here" as the destination, FAR. The challenge wording "how FAR he is asking him to travel" is also a pun on the airport code.

2-2. Jake — NaviLens (ddTag) colour code

The 80 x 87 px image is not a picture but a NaviLens marker. Inside a white quiet zone sits a black square containing a 5 x 5 grid of Cyan / Magenta / Yellow / Black cells. Each colour encodes 2 bits.

Symbol Colour Bits
C Cyan 00
M Magenta 01
Y Yellow 10
K Black 11

The four corner cells carry the palette and orientation, the centre cell carries the size, and the remaining cells of the centre row/column carry the CRC. The message is read from the remaining cells, each column top-to-bottom, columns left-to-right.

Grid as read:

C K M M M
K M M M M
K Y C C C
M K K Y K
K M M Y Y

→ 24-bit message 110111011101010110100111 = 0xDDD5A7

Because of the low resolution one cell was misclassified and the CRC disagreed. The automatic reader classified row 3, column 2 as Cyan, under which the stored CRC 0xC5D0 did not match the computed 0xE5D0. Treating that cell as Yellow makes them agree. Since the corrected cell lies in the CRC area, the message ID itself is unchanged. (CRC parameters: polynomial 0xC867, init 0, no input/output reflection, final XOR 0.)

2-3. ID → place lookup

A NaviLens marker carries only an ID, so the registered record must be queried. We opened the Android app with JADX to recover the request path and signing scheme (NaviLensAPIInterface, TagPetition, BaseAPI, NaviLensSignatureManager, CONSTANTS).

POST https://cloud.navilens.com/securized/services/tags/info
Content-Type: application/json; charset=UTF-8
x-date: <UTC timestamp>
authorization: Bearer <signature>

String to sign (joined with LF):

POST
/securized/services/tags/info
<lowercase hex MD5 of the body bytes>
application/json; charset=UTF-8
<same UTC timestamp as x-date>

signature = Base64(HMAC-SHA512(client signing constant from the app, string above))

The key is the literal bytes of the app's constant string (it is not hex-decoded first).

5. Interpretation caveats (limits of the evidence)

  • EXIF GPS is not the subject's location. Jonathan's image retains EXIF GPS pointing at 27.797469, -82.293686 (Hillsborough County, Florida). However GPSHPositioningError ≈ 5,094 m and there is no landmark at that coordinate. This is a trace of where the printout was photographed, not the meeting place. We used the boarding pass destination, FAR.
  • Choosing the destination is an inference. The PDF417 only establishes an ORD → FAR itinerary; FAR was taken as the meeting point from the "meet me here" context.
